# 세무쟁점 학습노트 첫 50개 신규 집필 실행계획

> 상태: 계획 수립. 원고 생성·사이트 변경·배포는 시작하지 않았다.
> 상위 설계: [세무쟁점 학습노트 범용 설계](../specs/2026-09-06-general-tax-learning-note-design.md). 집필·검수 기준은 상위 설계를 따르며 여기서는 이번 제작 범위와 산출물만 정한다.
> 실행 담당자는 `superpowers:executing-plans`를 사용해 아래 작업을 수행한다. 계획문서 저장은 집필·게시의 실행을 뜻하지 않는다.

**Goal:** 범용 설계로 우선 50개 학습노트를 처음부터 집필한다. 기존 원고의 표현을 보수하는 작업으로 대체하지 않는다.

**Architecture:** 쟁점 선정 → 공식 근거 조사 → 사례·질문·답·해설 공동 집필 → 근거 및 학습 검수 → 검수된 원고 인계로 진행한다. 사이트 이전·주소·데이터 변환은 원고 작성과 별도 작업이다.

**Tech Stack:** 원고는 Markdown, 검수와 출처 추적은 별도 기록으로 관리한다. Next.js·JSON 필드 등 현 사이트의 기술은 집필 양식을 결정하지 않는다.

## 1. 이번 작업 범위

- 우선 제작 물량은 50개다. 이는 이번 실행의 목표이며 범용 설계의 제한이나 장기 상한이 아니다.
- 대상 법률은 국세기본법·국세징수법·법인세법·소득세법·부가가치세법이다. 법령별 10개씩 배분하지 않는다. 다른 세목 추가는 별도로 범위를 정한다.
- 기존에 다루던 주제는 후보로 검토하되 제목·범위·사례·질문·결론·문서 간 경계를 유지할 의무는 없다. 필요한 기초·실무 쟁점을 선정해 제작 목록을 정한다.
- 기존 노트와 새 노트는 일대일 대응할 필요가 없다. 중복은 통합하고 독립적인 판단은 분리할 수 있다. 첫 제작 목록에 넣지 않은 중요한 주제는 후속 후보로 남긴다.
- 충분히 검수하지 못한 내용을 물량 달성 때문에 공개하지 않는다. 미완료·보류는 그대로 보고하고 다른 필요한 후보를 검토한다. 숫자만 채우는 문서를 만들지 않는다.
- 이후에는 같은 범용 설계로 추가 제작한다. 문서 수와 법령별 개수 제한을 새로 만들지 않는다.

## 2. 산출물과 역할

아래 파일은 향후 집필 실행에서 만든다. 이번 계획 편집에서는 만들지 않는다.

| 경로 | 역할 |
|---|---|
| `drafts/tax-learning/catalog.md` | 첫 제작 주제, 중심 판단, 대상 독자, 범위, 관련 법률, 기초 연결, 선정 이유, 진행 상태와 후속 후보 |
| `drafts/tax-learning/notes/{slug}.md` | 범용 설계에 따라 처음부터 집필한 학습자용 원고 |
| `drafts/tax-learning/research/{slug}.md` | 주장별 공식 출처·적용시점·판례 검토·계산 전제·확인 한계 |
| `drafts/tax-learning/reviews/{slug}.md` | 사실·질문·답·근거·효과 대조, 검수 결함, 보완 결과, 공개 가능 여부 |
| `drafts/tax-learning/handoff.md` | 검수 완료·보류·후속 후보 요약과 사이트 반영에 필요한 요구 |

`slug`는 선정한 주제를 식별하는 이름이며 이전 ID에 맞출 의무가 없다. 내부 자료와 학습자용 원고는 구분하고 내부 검수 메타를 본문에 넣지 않는다.

## 3. 실행 작업

### 작업 1. 제작 주제 선정

- [ ] 기본 다섯 법률 안에서 실무 빈도·기초 중요성·오류의 영향·분쟁·학습 공백을 고려해 후보를 수집한다.
- [ ] 후보마다 독자가 결정할 중심 문제와 본문 범위를 정한다. 같은 거래의 별도 판단과 단순 중복을 구별한다.
- [ ] 법령별 할당량 없이 첫 제작 목록을 선정하고 `catalog.md`에 선정 이유와 후속 후보를 기록한다. 기존 제목이나 목차를 그대로 채택하는 것을 완료 조건으로 삼지 않는다.

### 작업 2. 근거 조사

- [ ] 주제별 법률·시행령·시행규칙의 실제 적용 규정, 예외, 부칙과 적용시점을 확인한다.
- [ ] 필요한 판례·심판례·행정해석·회계·신고 자료를 확인한다. 출처의 성격과 사실·법리·실무 효과의 근거를 구별한다.
- [ ] `research/{slug}.md`에 주장과 출처, 확인일, 적용시점, 중요한 차이와 불확실성을 기록한다. 기존 자료도 검증 없이 정답으로 승계하지 않는다.

### 작업 3. 신규 집필

- [ ] 각 주제의 학습 목표와 근거에 맞춰 사례 또는 개념 설명을 처음부터 설계한다. 필요한 선택 모듈만 고른다.
- [ ] 사례의 당사자·현실적인 금액·날짜·자료와 질문·답·해설을 함께 작성한다. 기존 문장을 치환·분할·순환 재사용하는 방식으로 집필을 대체하지 않는다.
- [ ] 필요한 실무 처리, 추가 사례, 중요판례를 해당 설명에 연결한다. 정해진 질문·사례·판례 수를 채우지 않는다.
- [ ] 성격이 다른 쟁점에도 범용 설계가 작동하는지 검토하면서 제작 목록 전체를 집필한다. 비용 인정 사례에 맞춘 양식을 절차·징수·개념 쟁점에 강제하지 않는다.

### 작업 4. 원고 검수

- [ ] 집필과 구분된 검수 단계에서 범용 설계의 공개 기준을 적용한다. 질문·사실·답·해설·근거·후속 효과를 대조한다.
- [ ] 금액·단위·날짜·계산·당사자 일관성, 조문과 판례 정보, 기준시점과 공식 출처를 확인한다.
- [ ] 초보자가 질문을 이해할 수 있는지, 설명이 충분한지, 변형 사례에 숨은 전제가 없는지 확인한다. 반복 문구·불필요한 안내·쓸모없는 모듈은 제거한다.
- [ ] `reviews/{slug}.md`에 발견한 결함과 처리 결과를 기록한다. 필수 근거가 없거나 핵심 오류가 남은 원고는 보류한다. 자동 점검이나 형식 통과만으로 검수 완료를 선언하지 않는다.

### 작업 5. 결과 인계

- [ ] 제작 목록과 원고·근거·검수 기록을 대조해 누락을 확인한다. 완료·보류·후속 후보를 구별하고 실제 수량을 보고한다.
- [ ] `handoff.md`에 검수 완료 원고와 남은 판단, 사이트 반영 요구를 정리한다. 생성 또는 검수하지 않은 원고를 완료로 표시하지 않는다.
- [ ] 원고 작성 완료와 사이트 반영·게시 완료를 분리해 보고한다. 현 사이트를 수정하지 않은 상태에서도 원고 제작은 독립적으로 인계 가능해야 한다.

## 4. 별도 기술 반영 작업의 경계

이 실행계획은 원고 제작 계획이다. 사이트 변경이 요청되면 검수된 원고를 기준으로 별도의 기술 구현·검증 계획을 수립한다.

- 기존 주소와 ID의 연결은 기술 인계 단계에서 정한다. 링크 유지를 위해 새 원고의 제목·구조·사례·결론을 제한하지 않는다.
- JSON 구조나 질문 유형 열거가 원고를 표현하지 못하면 기술 표현 방식을 조정한다. 원고를 기존 필드 수에 맞춰 축소하거나 불필요한 내용을 채우지 않는다.
- 전체 문서 수·법령별 개수·질문 수를 고정하는 프로그램 제한은 사이트 반영 전에 정리한다. 공개 목록의 실제 항목 수와 참조 정합성을 검사하도록 한다.
- 선택하지 않은 섹션·내부 작성 메타는 화면에 출력하지 않는다. 실제 모바일에서 사실관계 다음에 질문별 답·해설과 근거를 이어 읽을 수 있는지 확인한다.
- 기존 사이트의 콘텐츠 교체·주소 변경·배포는 별도 실행 범위에서 처리한다. 계획만 저장한 상태에서 재생성이나 게시가 완료됐다고 말하지 않는다.
